# drydock v0.1.0 — public release plan

Briefing for the next Claude session that will polish this project into a
shareable open-source release under `sideralith/drydock` on GitHub.

> **Status**: Pre-release. The infrastructure works end-to-end on the original
> developer's machine (`rai`, UID 1000, WSL2). This document describes what
> needs to change to make it shareable, with constraints, validation, and
> non-goals explicit.

---

## What drydock is, in one paragraph

A defense-in-depth containerized sandbox for Claude Code. It runs Claude in a
Debian 12 slim container with `/var/run/docker.sock` bind-mounted (DooD), so
the agent has full access to the user's Docker workflow against existing
project stacks, but **no access** to `~/.ssh`, `~/.aws`, `~/.gnupg`,
`~/.kube`, or other unrelated home paths. The agent's own hooks are
RO-mounted (it can't self-edit guardrails). Engram memory and Claude Code's
local state run from container-specific directories (`~/.engram-container/`,
`~/.claude-container/`), so host and container Claude sessions can run in
parallel without SQLite/WAL contention.

Multi-project: one image, many projects. CLI tool `drydock` resolves
`PROJECT_DIR` from cwd or arg at invocation time.

## Current state (snapshot)

### What works

- ✓ Container builds (`drydock build`).
- ✓ `drydock init <dir>` creates `.claude/settings.json` baseline per project.
- ✓ `drydock` runs Claude in cwd's project.
- ✓ Auto-detects `docs/` 9P drvfs sub-mount on WSL2 and applies the
  conditional overlay (`docker-compose.docs.yml`).
- ✓ Auto-triggers `drydock setup` (host-side init) on first run if missing.
- ✓ Engram split: container has its own DB (`~/.engram-container/`);

  T3 (host DB unmodified after container session).

  `.claude.json` mount was added 2026-05-12 after discovering that without it
  Claude Code inside the container couldn't find its config file, created a
  fresh ephemeral one, and "settings didn't persist" across sessions. Now
  the container sees the project list, onboarding flags, MCP servers, OAuth.

  the matrix predates the `.claude.json` fix — re-running it would benefit

### What's WSL2-specific (acceptable for v0.1.0; document caveats)

- `/var/run/docker.sock` path. Docker Desktop on Mac sometimes uses
  `~/.docker/run/docker.sock` symlinked from `/var/run/`. May work; needs
  verification.
- 9P drvfs detection is WSL2/Windows-specific. On Linux native, the check
  returns false and the overlay doesn't activate — correct behavior.
- gRPC FUSE bind-mount perf on Mac is different. Not tested.

## v0.1.0 acceptance criteria

The release is "ready to share" when:

1. **No hardcoded user paths**: a fresh user with a different `$HOME` and
   different `id -un` can clone the repo, run `install.sh`, and have it work
   end-to-end without manual file edits.
2. **LICENSE present** (MIT, already in repo).
3. **CONTRIBUTING.md present** with: how to file issues, how to PR, code
   style (shellcheck pass), where to discuss.
4. **`install.sh` works** via `curl -fsSL <url> | bash` AND via manual
   clone+inspect+run.
5. **`examples/` directory** with at least 2 minimal templates:
   - `examples/web-stack/` — a docker-compose project with backend + db
   - `examples/minimal/` — bare project with just `.claude/settings.json`
6. **shellcheck CI** passing in `.github/workflows/lint.yml`.
7. **README depersonalized**: Sideralith mention moves to footer/credit; the
   header is about drydock itself.
8. **Tag `v0.1.0` published** on GitHub with release notes.
9. **Engram is fully optional**: users without engram installed see zero
   error noise. `drydock setup`, `drydock run`, and `drydock` work cleanly
   without engram binary present. Engram mount activates only if detected.
10. **`CLAUDE.md` present at repo root**: drydock's own AI-agent constitution
    written in Mercadona-style (rule + WHY + consequence per hard constraint).
    Encodes the load-bearing decisions so future Claude sessions working on
    drydock have non-negotiable context.

## Constraints (DO NOT change without discussion)

These are load-bearing decisions from prior work. Re-deciding requires
specific reason:

- **Threat model = A**: defense against accidents, not adversarial. Don't add
  socket-proxy in v0.1.0 — that's v0.2.0 if there's demand.
- **Docker socket bind-mount**: critical for the use case (`make shell-api`
  works). Don't replace with HTTP proxy in v0.1.0.
- **Engram split via separate `~/.engram-container/`**: not via shared DB
  with locks. WSL2 9P fcntl unreliability is the reason.
- **Hooks RO overlay**: `~/.claude/hooks/` mounted `:ro` on top of the
  container's `.claude` mount. Keep this.
- **`drydock init [DIR]` = per-project** (git-style). `drydock setup` =
  host-side, auto-triggered. Don't revert this naming.
- **`__HOME__` placeholder** in `templates/default-settings.json` — used by
  `drydock init` with `sed` substitution. Keep this pattern.
- **The serendipilink branch `dev-post-dockerized-claude`** still has
  `.claude/settings.json` with substituted `/home/rai/...` paths in the deny
  list. That's intentional — that branch is pinned to the original setup.
  Don't backport changes there.

## Non-goals for v0.1.0

- Adapter pattern for other AI agents (Codex, OpenCode, pi.dev). v0.2.0.
- macOS first-class support. Best-effort, document limitations.
- Windows native (non-WSL2). Out of scope.
- Web dashboard / TUI. Out of scope.
- Auto-update mechanism. Out of scope.
- Docker socket proxy integration. v0.2.0.

## CLAUDE.md content guide (for SDD #3)

drydock's `CLAUDE.md` is the **constitution** for any AI agent working on
drydock itself (and for human contributors who want to understand non-obvious
constraints). It should follow the **Mercadona pattern** used in serendipilink
(engram memory #870, #872): each hard rule has three parts.

### The pattern

```markdown
- **Rule**: [the constraint, stated as a verb-imperative or a forbidden behavior]
  - **Why**: [the technical or product reason — not "because it's good" but
    "because X breaks if not"]
  - **Consequence of violating**: [concrete bad outcome with a real example
    when possible]
```

Goal: convert **documentation** (descriptive, ignorable) into **constraints**
(prescriptive with reasoning the reader can judge edge cases against).

### Worked example (synthetic — the structure, not real content)

This is what a Mercadona-style rule looks like fleshed out. Synthetic example
(a generic PHP convention, not drydock-specific) so it's safe to study without
needing the serendipilink reference file:

```markdown
### Strict Types (PHP)

- **Rule**: Every PHP file MUST start with `declare(strict_types=1);`.
  - **Why**: PHP coerces types silently (`"5" == 5` is `true`), masking shape
    bugs at trust boundaries (HTTP input, DB rows, queue payloads). Strict
    types convert silent coercion bugs into compile-time / parse-time errors.
  - **Consequence of violating**: latent runtime errors at boundaries; refactor
    cost grows over time; harder to layer static analysis later.
```

Note the texture: the WHY is *specific* ("`"5" == 5` is `true`"), not vague
("type safety is good"). The consequence names *what* goes wrong and *when*
("at boundaries", "over time"). A reader hitting an edge case can reason from
the WHY rather than blindly following the rule.

### Sections that drydock's CLAUDE.md should cover

Suggested skeleton (adapt to what's load-bearing for drydock specifically):

1. **Project identity** — what drydock is, threat model A (accidents not
   adversarial), explicit non-goals (no adversarial sandbox, no Mac
   first-class without testing, no Windows native).

2. **Architectural invariants** (each rule + WHY + consequence):
   - `~/.claude/hooks/` MUST be mounted `:ro` — agent can't self-edit
     guardrails. Why: otherwise the protection layer is illusory under
     adversarial behavior + bug-prone behavior. Consequence: lose the
     non-negotiable defense of tier-1 hook system.
   - Engram + Claude state run from `~/.{engram,claude}-container/` (NOT
     host's `~/.claude/`). Why: SQLite/WAL race risk over WSL2 9P fcntl
     unreliability + OAuth refresh contention. Consequence: data corruption
     or last-writer-wins lockout.
   - Docker socket bind-mount = root-equivalent on host. NEVER claim
     adversarial isolation. Why: a process with socket access can
     `docker run -v /:/host --privileged`. Consequence: false-sense-of-
     security + onboarding contributors with wrong threat model.
   - Engram is **optional**. drydock must run cleanly without it. Why:
     reduces barrier-to-entry for contributors; users may prefer other MCP
     memory systems. Consequence: lock-in to one specific MCP plugin =
     niche tool, not portable infrastructure.

3. **Code/tooling conventions**:
   - Bash: `set -euo pipefail` in every script. No `eval` over user input.
     No `bash -c "$untrusted"`. Why: bash is unforgiving; one bad expansion
     = subtle bug at scale. Consequence: production-impacting CLI bugs.
   - Compose: parameterize all paths via env vars, never hardcode paths from
     a specific user's home. Why: drydock is multi-user infrastructure.
     Consequence: blocks contributors entirely.
   - Docker: no daemon-in-container. Image stays minimal. Why: DooD via
     socket is the contract; running a nested daemon defeats the model.
     Consequence: breaks `make shell-api` against host stack.

4. **Threat model boundary (explicit)**:
   - drydock defends against **accidents**, not **adversaries**.
   - Anyone proposing adversarial protections (socket-proxy, gVisor,
     namespace isolation) must justify against the use case + show maintenance
     cost. Why: scope creep destroys minimal tools. Consequence: drydock
     becomes a sandbox-platform meta-project, drifts from its niche.

5. **Tracking & contribution**:
   - GitHub issues + PRs OK (unlike serendipilink which uses docs-only). Why:
     drydock IS an open-source community tool — issue discoverability matters
     for contributors finding bugs.
   - Conventional commits, NO `Co-Authored-By`, NO `--no-verify`.

6. **Personality (optional)**: Spanish rioplatense / voseo if Rai is the
   primary maintainer. Warm but direct. (Tone reference: serendipilink's
   CLAUDE.md Personality/Tone sections — readable only on host Claude, not
   in the drydock container. For a public OSS project, consider a more
   neutral English-default tone; the maintainer decides.)

### What to NOT put in drydock's CLAUDE.md

- Anything project-specific to one user (paths, secrets, personal preferences
  beyond tone).
- "Aspirational" rules without enforcement. If a rule exists, the CI should
  enforce it or the rule shouldn't be there.
- Long-form architecture explanation (that belongs in `README.md` or in
  this `docs/` directory).

## Engram team memory pattern (for SDD #4 / CONTRIBUTING.md)

drydock should ship with a documented pattern for contributors to share
engram memories without requiring central infrastructure. Engram supports
this natively via the `sync` subcommand.

### How it works

```bash
# Maintainer: after closing an architectural decision relevant to drydock:
cd ~/git/drydock
engram sync --project drydock              # creates a chunk in .engram/
git add .engram/
git commit -m "sync engram memories: <topic>"
git push

# Contributor (who uses engram):
git pull
engram sync --import                       # absorbs new chunks into their local DB
# Now `engram search` returns the maintainer's drydock memories in their tool.

# Contributor (who does NOT use engram):
# .engram/ directory is ignored — drydock works fine without it.
```

### Implementation notes for SDD #4

- `CONTRIBUTING.md` documents this pattern as **optional**.
- The repo commits `.engram/` chunks to git. They're text-based / binary-
  diffable. Small overhead per commit.
- `.gitignore` does NOT exclude `.engram/`. Default `git add .` picks it up.
- `examples/` directory does NOT include `.engram/` — that's project-level,
  not per-example.

### What this is NOT

- Not "engram cloud sync" — that requires self-hosted engram server. Out of
  scope for v0.1.0.
- Not a hard requirement — drydock works for users without engram entirely.
